## 2026-11-27 - Performance phase 3: time across CPUs and in nanoseconds; GPU fence page (libdrm 2.4.124-6)

- Problem, time: the brief assumed `system_time()`, `clock_gettime()` and `gettimeofday()` still made a system call. They did not: Haiku already reads the TSC in user space with the factor and real-time offset from the commpage (`docs/KERNEL.md`, "Time in user space"); ARM64 and RISC-V read their counters in user space too. What was wrong: `clock_gettime()` had microseconds only, and the clock was not in order across CPUs. Haiku writes 0 into every CPU's TSC at boot; in QEMU/KVM one CPU ended 145 to 864 ns behind the others, so a thread on that CPU read an earlier time than another thread had read before it, also through the kernel's own `_kern_system_time()`.
- Change, time (x86_64): `arch_cpu.cpp` first runs a warp check on all CPUs (Linux's `check_tsc_warp` method, 2000 rounds per CPU under a lock). No step back: the TSCs stay as the firmware or hypervisor left them, and `system_time()` counts from CPU 0's TSC at that moment, `gX86TscBase`, which the kernel passes to libroot's `system_time.cpp` (`__x86_setup_system_time_base`, hidden) and publishes in the commpage (`system_time_tsc_base`, appended to the private `arch_real_time_data`). A step back: the old reset to 0. The kernel logs `tsc warp <n> cycles at boot, kept the firmware TSCs` or `reset the TSCs to 0`. `clock_gettime(CLOCK_MONOTONIC/REALTIME)` now use `system_time_nsecs()` (nanoseconds; truncated to µs equal to `system_time()`), `clock_getres()` says 1 ns for them. No seqlock was added: the factor never changes after boot and the real-time offset is one aligned 64-bit word set with `atomic_set64`; R5 has no NTP slewing and no suspend to RAM. A system-call fallback would read the same TSC, so there is none. Files copied from Haiku into `distro/kernel` with SPDX snippets: `libroot/os/arch/x86_64/system_time.cpp` and `time.cpp`, `posix/time/clock_support.cpp`, `kernel/arch/x86/arch_real_time_clock.cpp`, `headers/private/system/arch/x86_64/arch_real_time_data.h`; `arch_cpu.cpp` and `arch_timer.cpp` were R5 copies already.
- Problem, GPU: every fence or syncobj wait, also one with timeout 0 on work that had finished, was an ioctl that takes the kernel's GPU lock. RADV polls fences that way.
- Change, GPU: additive R5 GPU call `R5_GPU_FENCE_PAGE` (`+ 34`). One read-only area per team (`B_READ_AREA | B_KERNEL_AREA`, as the commpage), one 4 KiB block per open file with its 128 syncobj slots (point, submitted, LIVE, PENDING), its own retired sequence, GONE and CLOSED; nothing of another team, no kernel address, no global ring number. `gpu_unlock()` writes the blocks that changed under a seqlock, so a block is the state any call of that moment would see. A loss, a reset, the GPU off: GONE, every answer from the kernel. A closed file: CLOSED and a new generation, the area stays mapped while the team lives. libdrm-r5 answers from the block, without ioctl and without the lock: `SYNCOBJ_WAIT` and `SYNCOBJ_TIMELINE_WAIT` when decided (signalled, or not signalled at timeout 0), `SYNCOBJ_QUERY`, and `WAIT_CS` and CS dependencies at or below the file's retired sequence; every other case asks the kernel as before. The wait rule is the kernel's, as inline functions in `r5_gpu.h`. A syncobj wait that timed out is no longer printed to stderr unless `gpu_trace` is set. Docs: `docs/GPU-ARCHITECTURE.md` "Fence page", `distro/gpu/COMPAT`.
- Package: `libdrm-2.4.124-6`. Found while building it: `-5` was built on 21 Nov, so the libdrm part of phase 2 (#4696: `SYNCOBJ_BATCH`, the cached static info, the 27 Nov review fixes) never reached a package; `-6` carries it. Built in a private copy of the libdrm tree (`~/r5os/goofy-libdrm`), `check-libdrm-symbols.py` `ok libdrm symbols`, 222 exported symbols as before, pinned in `distro/packages/packages.sha256` (sha256 `26b026c1…`). Published with the owner's OK on 27 Nov 2026 by `scripts/publish-package.sh` as the pre-release `pkg-libdrm-2.4.124-6`; the asset was downloaded again and its sha256 matched the pin.
- Tested, host: `scripts/test-r5-fence-page.sh` (WSL): a fake kernel with the wait rules copied from `r5_gpu_core.cpp`; 400,000 random states and calls, the answer with the block equals the kernel call in every one, 138,636 answered without an ioctl (51,972 of 199,758 waits); three deliberate mutations of the rule (PENDING, timeline target, FOR_SUBMIT) are each caught; seqlock under a writer thread: 6,000,000 reads, 0 torn; closed block with a new owner, `DRM_IOCTL_VERSION` and a kernel without the call all re-ask or fall back; 19 ns per decided wait on the host. The existing library test (`test-ac-drm.c` with `test-r5-libdrm.c`, built in a temp folder against the shared host objects, nothing written in the shared tree): `ok libdrm ioctl`.
- Tested, QEMU/KVM (`-cpu host -smp 4`, private image copy, Skia on Lavapipe; `scripts/qemu-stability-tests.py` with `STAB_GUEST=scripts/perf3-guest.sh`, `STAB_ROOT=scripts/perf3-root.sh`): `scripts/build-locked.sh` `jam_exit=0`, `mesa_exit=0`, `ok egl vendor`, the image has `libdrm-2.4.124-6`. Kernel log `tsc warp 0 cycles at boot, kept the firmware TSCs`. `time_test`: user path 43.9 to 56.6 cycles per call against 199.7 to 238.7 through a system call (4.4×); 773,825,943 reads under load with 0 steps back within a thread and 0 across CPUs (before the TSC change 361 and 759 million, worst 212 and 864 ns); 14,630,000 checks agree with the kernel's clocks; the real-time step of one hour as root moved `CLOCK_REALTIME`, `gettimeofday()`, `time()` and the kernel's clock and left the monotonic clock alone. Desktop, Aomi (example.com), GLTeapot and VulkanTeapot (`--selftest` exit 0, llvmpipe) on screen, no debugger, no crash report.
- Limits: QEMU has no render node, so the kernel side of the fence page (the area, the publish at unlock, CLOSED and GONE, the reset path) is built but has not run. Only the 5625U can prove: a RADV client mapping the page, waits answered from it (fewer ioctls under `gpu_trace`), VulkanTeapot and Zink still correct, a hang/reset with GONE (`gpu_hang_test`), and the TSC warp result on real firmware. The X1, ARM64 and RISC-V were not tested. A 32-bit compat libroot would not know the TSC base; R5 builds none.

## 2026-11-27 - Network: a program started without network resolves names once the network is up

- Problem (owner, 5625U): Aomi started without Wi-Fi never loaded a page after Wi-Fi came up; only a restart helped. Reproduced in QEMU with the cable out at boot: Reload after the cable went in still gave "client error (Connect)".
- Cause 1: Haiku's resolver keeps every `res_state` it built. NetBSD reloads `resolv.conf` when it changes (`res_check()` with a kqueue); Haiku has no kqueue and builds `res_init.c` without it, so a state built while there were no name servers stayed empty for the life of the process. This hits every program, not only Aomi.
- Change 1: `distro/rest/src/system/libnetwork/netresolv/resolv/res_state.c` (R5 copy, NetBSD licence kept, R5 part MIT in SPDX-Snippet): each pooled state (`__res_get_state()`, used by `getaddrinfo()` and `gethostbyname()`) remembers the `resolv.conf` it was built from (inode, size, modification time) and is built again when the file is another one. One `stat()` per lookup. The shared `_res` (`__res_state()`) stays as Haiku has it (review of PR 4707: rebuilding it lost a program's own options and raced between threads).
- Cause 2: R5's `NetServer::_ConfigureResolver()` keeps one block per source and assumed IPv4 DHCP sends no `device`. Haiku's `DHCPClient` does, so SLAAC or DHCPv6 on the same interface replaced the IPv4 name server; QEMU ended with only `nameserver fec0::3` and no page loaded (curl failed as well).
- Change 2: `distro/rest/src/servers/net/NetServer.cpp`: an update without an IPv6 server is the IPv4 block of its device, tagged `ipv4:<device>` (`ipv4` when it names none), so two IPv4 networks keep their own servers. An IPv4 update also replaces the blocks an older NetServer wrote for it (`ipv4`, and IPv4 servers under the bare device). QEMU afterwards: `fec0::3` under the device and `10.0.2.3` under `ipv4:<device>`.
- Change 3 (Aomi): a tab whose load failed (Servo's "Error loading page", now titled "Page could not be loaded") loads again by itself: when the network changes (`start_watching_network()`), when the folder of `resolv.conf` changes (`watch_node()`), three times 3 s apart, and every 15 s for five minutes while the error page shows (a network does not always report that it came back).
- Mistake on the way: the first two runs relied on the notices only. In QEMU they all came at boot; when the network returned nothing changed that could be noticed, so the page stayed on the error. The 15 s retry was added after that.
- Tested (QEMU, KVM, usernet, private image copies, `scripts/qemu-aomi.py` with `scripts/aomi-review-guest.sh`): before (image from main before this branch) the interface came back with DHCP, Reload still failed, `resolv.conf` held only `nameserver fec0::3`. After: `resolv.conf` holds `fec0::3` (device block) and `10.0.2.3` (`ipv4` block); Aomi, started with the interface down, logged "network back: tab 0 loads https://example.com/ again" and showed the reload under way 40 s after the network returned; the page then showed Example Domain (a scripted Reload followed, so which of the two finished first is not known). Not tested on Wi-Fi or on the 5625U.

## 2026-11-27 - libroot: thread_local destructors after dlclose() (GitHub #3012)

- Problem (Haiku #18182): libroot had no `__cxa_thread_atexit_impl`, so libstdc++ used its own `__cxa_thread_atexit()` list, which does not keep the library loaded. A library unloaded with `dlclose()` while a thread still owned one of its `thread_local` objects made that thread call into unmapped code at its end. R5 can hit it: the compositor unloads Lavapipe on a fallback, and Servo uses `thread_local`.
- Change: libroot (`distro/kernel/src/system/libroot/os/thread.c`) has `__cxa_thread_atexit_impl()` and `__cxa_thread_atexit()`. Each thread keeps its list in a new reserved TLS slot `TLS_THREAD_DTORS_SLOT` (after `TLS_STATIC_TLS_READY`; the TLS fast path of #4697 is unchanged). The destructors run at thread exit before the on-exit callbacks, the pthread keys and the TLS blocks, and in `exit()` before the static destructors (`distro/rest/src/system/libroot/posix/stdlib/exit.cpp`). libroot counts pending destructors per library under its own mutex. `dlclose()`/`unload_add_on()` (`distro/rest/src/system/runtime_loader/elf.cpp`) ask it through `thread_dtors_pending_in_range` in `rld_export`. A library with pending destructors, or a dependency only it keeps loaded, stays loaded for good, as with glibc. The runtime loader binds `__cxa_thread_atexit` to libroot for every image (`elf_symbol_lookup.cpp`), whatever the load order; libstdc++'s copy is not used anymore.
- Mistake on the way: the first version took a reference on the image through the runtime loader on every registration (its global lock) and gave it back at thread exit, which could unload a library from the exiting thread. With Skia on Lavapipe in QEMU, Aomi's window then never appeared (it existed and was not hidden, app_server drew nothing); with Painter, and on main, it did. A thread holding the loader lock (dlopen/dlclose and their init and atexit hooks, such as Mesa joining its worker threads) can wait for a thread that registers or ends. The final version never takes that lock when registering or running destructors.
- Tested: `distro/tests/libroot/tls_dtor_test` (`scripts/build-stability-tests.sh`) in QEMU KVM: a clean round (thread ends, then `dlclose()`) unloads the library; 200 rounds with `dlclose()` while the thread owns the object keep it and run each destructor exactly once. On a main image the same test stops in the debugger. Aomi opens example.com with Skia on Lavapipe and with Painter; GLTeapot and StyledEdit open. Two `scripts/build-locked.sh` builds (jam exit 0). Not run on the 5625U.
- Limits: a library closed while a thread still has its destructors pending is never unloaded afterwards (glibc does the same). A thread that is killed (`kill_thread`) runs no destructors.

## 2026-11-26 - exFAT: production correctness, crash-consistency, forced-unmount and SD/USB performance fixes

- Problem: Deep review of PR #4662 (exFAT write support) and PR #4674 (forced unmount on media pull) uncovered correctness, crash-consistency, concurrency and performance gaps:
  - `exfat_read_entry()` rejected `SecondaryCount > 17`, breaking 241–255 char filenames (`SecondaryCount == 18`) and benign secondary entries.
  - `DirectoryIterator::_NextEntry()` dereferenced `fBlock.SetTo()` without a NULL check (kernel panic on media pull), `_GetNext()` could overflow its stack buffer on malformed filename chains and failed to skip benign secondary entries.
  - `Volume::SyncDisk()` cleared `VolumeDirty` without committing open dirty inodes (`ValidDataLength` stayed stale on disk → zeroed reads after crash/unmount), in-place writes skipped `mtime` updates, `SyncDisk()` missed `B_IO_ERROR`/`B_DEV_MEDIA_CHANGED`/`B_DEV_WRITE_ERROR` on media pull, and `Volume::~Volume()` leaked all `fNodeTree`/`fInoTree` nodes.

## 2026-11-25 - exFAT write support (#4655)

Problem: Haiku's exFAT driver, used unchanged, always mounted read-only and its write hooks were null. On the 5625U (stick 83) Tracker refused copies onto a 116.5 GiB exFAT SD card.

Changed: the driver now lives under distro/ and can create, delete, rename, grow and shrink files and directories. VolumeDirty is set before the first write and cleared on a clean sync. A dirty volume, or one that fails the bitmap, up-case, TexFAT or media-failure checks, mounts read-only. A deleted file's inode key is dropped, mkdir releases its vnode, an unchanged-length entry is rewritten in place, and a cluster number outside the heap is refused. Loading a file uses the directory stream stored with its inode, not a recursive vnode walk. FindBlock returns a byte offset. A contiguous file yields at most 1 MiB, and at least the rest of the current cluster. A FAT chain stops at that same limit, so a contiguous chain is not walked to the end of the file. File bytes go to the card in whole sectors, through the device, and are not kept in the volume block cache. The writer mutex is separate from the inode lock, and that lock is not held across the file cache. Rename inside one folder uses one directory node, so a folder that has to grow keeps the new length. Rename of a folder over a non-empty folder returns B_DIRECTORY_NOT_EMPTY. Rename over a file frees the target's clusters when the vnode is gone. A case-only rename updates the directory that holds the file. A renamed file keeps its new name hash. Adopting the stream after a rename leaves the open vnode's valid length and its committed length alone, so a write that updates the length during the rename is not overwritten. A write through an unlinked open file does not rewrite the directory slot. An entry write publishes the committed valid length. Flush and close write the file's sectors to the card, then the entry's valid length, when that length changed. fsync writes the file cache even when the valid length did not change, so an overwrite inside the file reaches the card. After the file data, and again before the boot sector is marked clean, the drive cache is flushed. fsync flushes the drive once more after the directory entry and the other metadata. `B_DEV_INVALID_IOCTL` is success. The kernel reports that code to `ioctl` as `ENOTTY`, with -1 and the code in `errno`. `B_UNSUPPORTED`, `B_NOT_SUPPORTED` and `B_BAD_VALUE` are success too. Any other flush error still fails the close, the fsync or the unmount. A cached target is marked deleted only after its slot has been deactivated. A free slot returns B_BAD_VALUE and does not make the card read-only; a bad checksum on a live set does. A negative size is rejected. A shrinking truncate flushes cached pages before the entry changes, and the valid length becomes the shorter of the new size and the bytes already written. Freeing a fragmented file flushes each bitmap block and each FAT block once.

Mistakes: the first write path returned a sector number where the file map expects a byte offset, so a read or a copy would have used the wrong blocks. Rename over a file removed the new name as well and could free clusters twice. A case-only rename in a folder wrote that slot in the parent folder. The inode lock was held across file_cache_write, which deadlocks with the page writer. The cached name hash was left behind after rename, so the next size update failed and could mark the volume read-only. A rename that grew its own folder kept the old length, so the new name was invisible and the next create could overwrite the cluster. Rename of a folder over a non-empty folder dropped the target's entries. A file published before its cache existed faulted in file_cache_read (page fault at file_cache_read+0x15); the cache is created after publish_vnode. Sending a short run to the raw device returned B_BAD_DATA; the device is now given whole sectors, and a 12-byte read bounces one sector. Putting file bytes in the volume block cache left the valid length on the card while the bytes were still only in memory. The in-memory valid length on rename was read from an inode table that nothing inserts into, so an open file dropped back to the length on disk. Saving that length and writing it back afterwards could still lose a length the writer stored in between. A shrinking truncate published the new size as valid even when fewer bytes had been written. fsync returned before the data when the valid length was already the one on the card, so an overwrite inside the file stayed in memory. ## 2026-11-25 - A changing bitmap was kept as the previous texture

Problem: On the 5625U (stick 81, main `dd905a39c3`, build 10072) VulkanTeapot on RADV stepped on screen while its title counted more than 300 frames a second. The same step was reported for GLTeapot on RADV on 19 Nov and was not found then. The frames are drawn. They do not become the picture on screen at that rate.

Cause: Skia keeps a texture for a client `BBitmap` and checks it with 64 samples (`bitmap_sample` in `distro/app_server/skia/SkiaPainter.cpp`). The stride was `length/64` bytes. On VulkanTeapot's 384 by 384 `B_RGBA32` bitmap that is exactly 6 rows, so every sample is the first eight bytes of a row and the tail is the last eight bytes. The teapot is drawn in the middle and that border stays the clear colour, so the sample never changes. `FindTexture` returns the previous upload. The full hash runs only on every 32nd lookup, so the window steps about ten times a second. The title counts `draw_frame` plus `Invalidate` and does not wait for that draw. A host check of the old stride on a 384 by 384 picture, changed only in the centre, produced the same sample; the new 8 by 8 grid on a 1920 by 1080 picture does not. A bitmap of at most 1 MiB is now hashed in full, so this picture cannot miss.

What changed: the sample. Nothing in the GFX9 ring, the PSP, the page tables, the reset or the stop. The software path is Painter, which reads the bitmap on every draw and does not use this cache. GLTeapot on llvmpipe writes the direct-window front buffer and does not come through here. While a direct window has paused the compositor, its view bitmap is drawn by Painter and copied to the front on `SetViewBitmap`; that path is unchanged.

Hardware and Lavapipe are not the same path. The step was seen on the 5625U, on RADV. The sample itself is one function in app_server, so Skia on Lavapipe and Skia on RADV check a bitmap the same way. That check does not explain a desktop that steps only on the machine. What the machine does and QEMU does not: `_ScanoutPrepare` returns at once when the compositor is on Lavapipe, and the GPU copy onto the firmware scanout does not run. Stick 81 logged both (`scanout through vulkan 1920x1080`, `gpu copy on scanout`). The title does not wait on that copy, on FIFO, on the 16667 us compose period, or on `Window::EndUpdate`. A smooth Lavapipe teapot does not show that those two hardware steps kept up.

Limits: Not booted on the 5625U again. If the teapot still steps there and Lavapipe stays smooth, the sample was not the whole cause and the leftover is the scanout on that machine. A direct window that still steps is a different path. The next stick shows the fix by the teapot turning smoothly while the title still counts frames; there is no new syslog line. `gpu_debug` stays off by default and was not given new counters.

Tested: `scripts/build-locked.sh` compiled `SkiaPainter.o` and linked `app_server` (25 Nov 2026, 13:29 Europe/Amsterdam). The image was written. `install-mesa-packages.sh` then exited 1 because the image contains `vulkanteapot-1.0.0-6` and that script still requires `vulkanteapot-1.0.0-5`. ## 2026-11-23 - Card reader: an SD card put in again is found

Problem (stick 77, 5625U, main `a08d00b67c`, `generated/boot-5625u-77/` in the stick worktree): the SD card that was in at power on was found (`SDHC card found`), read, and shown in the mount menu. After the card was taken out and put in again, every command failed: `rtsx: CMD7 (arg 00000000) failed: Operation timed out` three times, then `CMD55 failed`, and the card was not found again. Mounting the exFAT volume then failed with `read of 512 bytes at 16777216 failed: Operation timed out` and an I/O error.

Cause: mmc_bus remembers the selected card (RCA 1). Before each bus command (RCA 0) for the new card it first sends CMD7 with RCA 0 to deselect the old one. No card answers CMD7 with RCA 0 (SD physical layer; OpenBSD sdmmc sends it without a response), but rtsx waited for an R1b answer. The timeout made `_ActivateDevice()` fail, so mmc_bus sent neither CMD0 nor any other command to the new card. At the first scan no card was selected yet, so no CMD7 was sent.

Changed, after a review of the whole card path (rtsx, mmc_bus, mmc_disk) against the SD physical layer:

- rtsx (`rtsx_haiku.cpp`): `response_type()` takes the argument; CMD7 with RCA 0 has no response (`RTSX_SD_RSP_TYPE_R0`), CMD7 with an RCA stays R1b.
- mmc_bus (`mmc_bus.cpp`, and `mmc_bus.h` now copied into `distro/`, Haiku MIT with R5 snippets): CMD0 puts every card in the idle state (no card selected, RCA and 4 bit bus gone). Each scan now first forgets the selected card, so no CMD7 is sent on any host (sdhci too), and removes the node it published for the last card (`_RemoveCard()`, `unregister_node` with the bus lock released). Before, a card put in again came back on its old node (the device manager found the same attributes), so `mmc_disk` never read its size or set the 4 bit bus again (1 bit after the scan's CMD0, and the old size for a different card).
- mmc_disk (copied into `distro/`, Haiku MIT with R5 snippets; `scripts/apply-kernel-bugs.py` installs both new copies): a `device_removed` hook marks a removed node; its I/O and trim then return `B_DEV_NO_MEDIA`, so a volume still mounted from the old card cannot write to the new one, and `B_GET_MEDIA_STATUS` says `B_DEV_NO_MEDIA` instead of always `B_OK`. A trim ended at `offset + length`, but CMD33 takes the last block to erase, so it also erased the block after the range; it now ends at the last block (one sector, or 512 bytes on a byte-addressed card).
- rtsx (`rtsx.cpp`, R5 snippets in the ISC file): a transfer end that arrives after its waiter gave up (timeout, soft reset) is cleared right before the next command or DMA starts; before, the next command could return at once with the answer of no command. An erase (CMD38) may stay busy for 10 s instead of 1 s (SD erase timeout).

Limits: a removed card's node goes when the next card is put in, not at once (the rtsx driver has no call to tell mmc_bus about a removal); an open disk stays until it is closed. A short window remains in which an I/O that passed the check just before the removal waits for the bus during the scan of the new card. The write-protect switch is not read. Default speed only. Writing a file is not proven on hardware: the driver logs only reads. sdhci itself is unchanged (it also sends CMD7 with RCA 0 as R1b; mmc_bus no longer sends that on a scan, but `mmc_disk` still deselects before CMD9 when a card was selected).

Tested: not built and not booted yet; it goes on the next stick (card in, out and in again, mount, copy a file to it and read it back).
