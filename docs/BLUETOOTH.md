# Bluetooth on R5

This is the plan for Bluetooth on R5 Operating System: what is already in the tree, where each part goes, and the steps that get there. Each step is its own small pull request with a pass rule. The owner approved this plan; the choices in section 4 are the owner's.

Nothing in this document is built yet unless it says so.

## 0. Before step 0: VirtualBox USB passthrough and test hardware

QEMU has no Bluetooth hardware. Before step 0 we check USB passthrough in VirtualBox.

- The Windows host has the Oracle VirtualBox Extension Pack 7.2.22 (`Usable: true` in `VBoxManage list extpacks`). The `R5OS` VM already has `xHCI USB: enabled`, with no USB filter yet.
- Chosen: pass the built-in MT7922 of the 5625U to the VM (section 4, choice 4). The other options, for reference:
  - **CSR** (for example CSR8510 A10, `0x0a12:0x0001`, generic USB class `0xE0/0x01/0x01`): works in `h2generic` without extra firmware. Cheap CSR8510 clones often do not work, also not on Linux; buy one from a known brand.
  - **Realtek** (`0x0bda`): `h2realtek.cpp` loads the patch for a chip it knows (`docs/BLUETOOTH-2.md`, step B0). Only the RTL8761CU of the ASUS USB-BT600 (`0x0b05:0x1d70`) has its firmware in the image.
  - **Qualcomm** (`0x0cf3`): no firmware loader, so it does not work as a dongle.
  - **Intel** (`0x8087`): needs `bt_firmware` (see `h2generic.cpp`).
  - **MediaTek MT7922** (`0x13d3:0x3567` in the 5625U): `h2mediatek.cpp` is already in `distro/`. It is the built-in radio of the 5625U, which we also test bare metal from the USB stick. Passing it to VirtualBox takes Bluetooth away from Windows while the VM runs.
- **5625U bare metal (MT7922):** USB sticks are costly, so hardware tests on the 5625U are bundled into one stick per few steps. The owner writes the stick with `scripts/write-stick.py`, after VirtualBox works first.

## 3. Steps

Each step is its own small pull request. It is built for AMD64 with `scripts/build-locked.sh` (apply and jam under one build lock, `/home/nickr/r5os/.r5-build.lock`; never `apply-overlay.sh` and `jam-r5-raw.sh` one after the other), and kept building for ARM64 and RISC-V (not tested). QEMU runs only on an own copy of `r5-os.image`, never through `scripts/run-qemu-r5.sh`, which stops every QEMU.

**How the fuzzers run (steps 1a, 1b, 1c).** Like `scripts/fuzz-midi2.sh`, the Bluetooth fuzzers run in WSL on the host (`g++ -std=c++17 -fsanitize=address,undefined -fno-omit-frame-pointer -g -O1`). The kernel parsers (the `hci` event and packet parser, and the `l2cap` packet and signalling parser) are compiled on their own with small host stub headers (`-I scripts/bt-host`, like `scripts/midi2-host`), without the whole Haiku kernel. `scripts/fuzz-bt.sh` and `scripts/bt-host` are new in step 1a. Each target runs 60 seconds.

  6. `close(client)` in `SDPServer::_Run()`, and `>= 0` socket checks.

### Step 1a (PR 2): `h2generic` HCI timeouts, safe reassembly, HCI fuzzer

- **What:** in `distro/kernel/src/add-ons/kernel/drivers/bluetooth/h2/h2generic/`: a hard HCI command timeout. A command without a Command Complete or Command Status within 2 s (Linux `HCI_CMD_TIMEOUT`) gets a Command Status with error `0x1F` (Unspecified Error) for that opcode, the timeout is logged with the opcode, and a real answer that still comes later is dropped (`h2command.h`). In `distro/kernel/src/add-ons/kernel/bluetooth/hci/`: the packet reassembly moves to `hci_assemble.h`, without the `panic()` on a split event and without the endless loop on SCO.
- **Not in this step (owner, 15 Nov 2026):** the Event Mask and the LE Event Mask. An HCI Reset from the kit (`LocalDevice::Reset()`) clears what a driver sets, so `bluetooth_server` sets them after every reset: the Event Mask in step 4, the LE Meta event and the LE Event Mask in step 6.
- **Checked (16 Nov 2026), which events each step needs:** after a reset the Event Mask is `0x00001FFFFFFFFFFF`, bits 0 to 44 (Core 6.0, Vol 4, Part E, 7.3.1); bit *n* is event code *n* + 1. Steps 1a to 3b use only events in that default (command answers, inquiry results, connections). Steps 1b and 1c add LE fixed channels and CoC to `l2cap`, but no LE link exists before step 6 asks for LE events, so they are tested with the fuzzer and the ABI test only. Step 4 needs Secure Simple Pairing events that are not in the default: IO Capability Request and Response, User Confirmation Request, User Passkey Request, Remote OOB Data Request and Simple Pairing Complete (codes `0x31` to `0x36`, bits 48 to 53), User Passkey Notification and Keypress Notification (`0x3B`, `0x3C`, bits 58 and 59). `LocalDeviceImpl.cpp` already waits for some of them, so on a controller that keeps the default they never arrive. Step 5 needs nothing new. Step 6 needs LE Meta (`0x3E`, bit 61).
- **Required checks:** manual SMAP review, a QEMU boot with SMAP, and `scripts/fuzz-bt.sh hci 60` in WSL (60 seconds of ASan and UBSan on the separately compiled HCI event and packet parser).
- **Pass:** QEMU SMAP boot without kernel panic, log line `hci_fuzz: 60s 0 crashes`, and in VirtualBox with the passed-through radio: `h2generic: controller ready`.

### Step 1c (PR 4): `l2cap` CoC and EATT, ISO endpoints prepared

- **What:** LE credit-based flow control (CoC) in `distro/kernel/.../l2cap/`, and recognition of the ISO USB endpoints in `h2generic`.
- **Pass:** QEMU SMAP boot, `l2cap_fuzz: 60s 0 crashes`, and `l2cap_coc_test: ok`.
- **Moved (16 Nov 2026, while the owner slept; open to change):** this step runs just before step 6, not after 1b. CoC and EATT run over the LE signalling channel of an LE link, and the ISO endpoints carry LE Audio (step 7); no LE link exists before step 6 asks for LE events, so nothing could use or test them earlier than the fuzzer. Built next to step 6, CoC shares the fixed-channel socket interface and gets a real LE link to test against.
- **As built (16 Nov 2026, one branch with step 6; nothing on hardware yet):**
  - **LE links in the kernel.** `btCoreData` (now in `distro/`) registers an LE link from LE Connection Complete and both Enhanced Connection Complete events, as an `HciConnection` of type `R5_HCI_LINK_LE` whose address is a `sockaddr_l2cap_le` (with the address type). It keeps the LE buffer length from the answer to LE Read Buffer Size, and `PostACL()` splits LE packets by it. Found while building: `AddConnection()` added a connection that already existed (data before the Connection Complete event) to the list a second time, which breaks the list; fixed.
  - **The socket interface** is `<R5BluetoothLE.h>` (private header, MIT): `sockaddr_l2cap_le` with channel, address type and mode. A fixed-channel socket (ATT `0x0004`, SMP `0x0006`, uid 0 only, one each) gets every PDU of that channel from every LE link with `recvfrom()` and sends with `sendto()`; bluetooth_server holds both. The LE signalling channel `0x0005` is served in the kernel: Connection Parameter Update (accepted within the limits of Vol 6, Part B, 4.5, then LE Connection Update), LE credit-based (`0x14`, `0x15`) and enhanced credit-based connections (`0x17`, `0x18`, up to five channels, the mode EATT uses on PSM `0x27`), Flow Control Credit and Reconfigure. Credit-based channels split an SDU into K-frames by the remote's MPS and credits and put received frames back together (`l2cap_coc_rx_frame()` in `l2cap_parse.h`, also in the fuzzer); a frame without a credit, too long, or past its SDU closes the channel. Our side: MTU 1024, MPS 247, 10 credits, given back while the receive queue has room.
  - **Fixed on the way** (Haiku code): closing a socket that was bound but never listened asked a command identifier of a NULL connection; a full receive queue leaked the buffer; `_SendQueued()` wrote the L2CAP header into a buffer `PostACL()` already owned; `htole32` was the 16-bit swap. From the independent review: the HCI receive thread holds the device list lock while it delivers a packet up, and every L2CAP sender held its endpoint lock while `PostACL()` took that list lock, a deadlock (also for Classic); L2CAP now sends through one send thread, `l2cap_tx.cpp`, without its locks. A packet is matched to the link it came on (no longer the first link of its address), and a channel only takes data, a disconnection or a configuration from its own link.
  - **Not in this step:** the ISO USB endpoints of `h2generic` (LE Audio, step 7). bluetooth_server uses the fixed ATT channel for GATT; EATT channels can be opened through the socket, but bluetooth_server does not open them yet.
  - **Checks:** `scripts/fuzz-bt.sh l2cap 60` (now with the LE codes and the frame reassembly), `bt_l2cap_coc_test` in QEMU with SMAP, manual SMAP review (no new user pointer in the kernel: addresses come through the socket layer, which copies them).

### Step 5 (PR 9): Classic A2DP (R5's own MIT SBC) and AVRCP in `bluetooth_audio`

- **What:** a royalty-free SBC encoder (R5's own MIT code), AVDTP 1.3, and AVRCP (play, pause, volume) in `distro/media/bluetooth_audio/`, with an audio output choice per user. A real-time audio thread, and background scans paused while streaming.
- **Test path:** first VirtualBox USB passthrough, then a bundled 5625U bare-metal stick (written by the owner with `write-stick.py`) with the Sony WH-1000XM3 or XM4.
- **Pass:** log line `bluetooth_audio: streaming sbc 44100Hz`, steady audio without stutter on the Sony XM3 or XM4, and `bluetooth_audio: stream closed cleanly` on disconnect.
- **As built (16 Nov 2026; nothing on hardware yet, because Classic pairing on the MT7922 (reworked in #4314) is not yet confirmed with a headset):**
  - **SBC** (`sbc_encoder.cpp`, MIT): written from the A2DP 1.3.2 appendix B only. The analysis runs in floating point on the mixer's float samples, so nothing is rounded to 16 bits before SBC quantizes. All modes, 4 to 16 blocks, 4 and 8 subbands, Loudness and SNR, bitpool 2 to 250. The prototype filter is kept as the filter itself; the folding sign of the printed window is applied in code, with the reason in a comment.
  - **Quality choice** (`a2dp_proto.h`, `ChooseConfiguration()`): only the mixer's rate, 44.1 kHz, which every sink must have; R5 offers no other rate because it does not resample. Then joint stereo, 16 blocks, 8 subbands, Loudness, and the highest bitpool the headset allows within A2DP 4.3.2's 512 kb/s and one 672-byte media packet. That is bitpool 86 (509 kb/s) when the headset allows it, and the headset's maximum otherwise (53, 328 kb/s, on most). If the headset refuses its own maximum, R5 tries again once with 53, the A2DP high quality setting.
  - **AVDTP 1.3** (`A2DPSource.cpp`): one SBC source endpoint, as initiator (Discover, Get All Capabilities with a fallback to Get Capabilities, Set Configuration, Open, the media channel, Start) and as acceptor for every command a sink sends (including Delay Report, Abort and a General Reject for unknown ones). Only single-packet signalling. **Correction to the brief:** `bluetooth_server` did not listen on PSM `0x19`; the add-on listens on `0x19` and `0x17` itself while its node exists. `bt_l2cap_abi_test` now accepts `0x19` as held by bluetooth_audio.
  - **Who may connect:** the headset chosen by the person who signed in, or, with no choice, any paired device; in both cases only on an encrypted link (`BT_MSG_R5_AUDIO_PAIRED` says paired, connected and encrypted; uid 0 only). R5 waits up to 5 s for encryption after a headset connects. Anything else is refused and logged without the address.
  - **Real-time thread** (`B_REAL_TIME_PRIORITY`): encodes and sends at the audio clock, 20 ms ahead, from a 40 ms ring; an empty ring is sent as silence so the headset never starves, and a ring that grows from clock drift is trimmed. The node reports that latency plus the headset's reported delay (capped at 0.5 s), so video stays in sync. After 5 s of silence the stream is suspended so the headset can sleep; the next sound starts it again, keeping the last 150 ms.
  - **Scans paused:** while the stream runs, `bluetooth_server` refuses Inquiry and Periodic Inquiry (`BT_MSG_R5_AUDIO_STREAMING`, uid 0 only, ends by itself when media_addon_server's team is gone). A scan that already runs is not stopped.
  - **AVRCP** (PSM `0x17`): R5 asks for the headset's events and registers for volume changes; with absolute volume the node's Volume parameter is the headset's volume (R5 takes the headset's level first, never jumps to its own), without it the gain is applied to the samples. Play, pause and stop from the headset are accepted and start or suspend the stream. UNIT INFO and SUBUNIT INFO are answered; other PASS THROUGH keys get NOT IMPLEMENTED.
  - **Output choice per person:** `~/config/settings/Media/bluetooth_audio` (flattened BMessage, `device`). media_addon_server runs as uid 0, so the add-on reads the file of the account Login named in `/boot/system/settings/r5-desktop-session` (as the registrar does) and never writes it. The person writes it with `bt_audio use <address>` or `bt_audio off` (`find_directory(B_USER_SETTINGS_DIRECTORY)`).
  - **Log lines:** `bluetooth_audio: streaming sbc 44100Hz`, then the mode, blocks, subbands, bitpool and rate; `bluetooth_audio: stream closed cleanly` after Close in either direction; `bluetooth_audio: stream ended: <reason>` otherwise. No addresses or keys.
  - **Review of #4317 (16 Nov 2026), fixed:**
    - Reaching the chosen headset: the L2CAP socket only uses a link that is already up (`btCoreData` has no Create Connection). The new `BT_MSG_R5_AUDIO_CONNECT` (uid 0) makes bluetooth_server bring up the link to a paired headset without pairing. Classic only, so a dual-mode headset is not paired over LE, and with no pairing window. R5 then waits up to 15 s for the encrypted link.
    - SDP: `SDPServer` read requests and never answered them. It now answers from fixed records (`SDPRecords.h`): A2DP Audio Source (AVDTP 1.3, PSM `0x19`), AVRCP Controller (category 2, for the headset's volume) and AVRCP Target. Anything else gets an empty list, and a broken request gets an error. Continuation is supported, and every answer is at most 600 bytes.
    - Endpoints: a headset that lists AAC, aptX or LDAC first is asked for SBC on each free sink endpoint in turn.
    - Rate: only 44.1 kHz is offered, and a Set Configuration at another rate is refused (`0xC4`). Before, a headset could choose 48 kHz, and the 44.1 kHz audio then played too fast.
    - LE: an LE scan pauses while audio streams, like Inquiry does, and comes back afterwards.
    - Threads: the AVRCP thread reads with a 200 ms timeout, because `shutdown()` does not wake an L2CAP `recv()`. `_EndSession()` ends the session before it waits for that thread. `Start()` cleans up after a failure, and without AVDTP it fails.
    - Packets: when the headset's MTU is smaller than 672 bytes (`EMSGSIZE`), one packet is lost and the next ones carry fewer frames.
    - Clock drift: one sample less per packet instead of a jump of up to 80 ms.
    - AVRCP: GetCapabilities with Events gets an empty list, as AVRCP 1.6, 6.4.1 requires.
    - Smaller fixes: volume sends do not block the node's thread, and the node's volume and latency are atomic.
    - Not changed: the encoder's speed (finding 3.2). It does about 2 million operations per second, less than 0.1 % of one core.
  - **Open:** play and pause do not reach the playing program; the headset choice is not on the Bluetooth page yet; a Classic inquiry that already runs when the stream starts is not stopped (at most 13 s). ARM64 and RISC-V 64 were not built or tested.

#### Step 7: HFP (Hands-Free Profile) for classic headsets

**What the person gets:** the headset's battery level in the Bluetooth page and in Deskbar (7b), the headset's buttons for calls and its volume (7b), and later its microphone as an audio input (7c). A headset like the Sony WH-1000XM4 sends its battery only over HFP: A2DP carries no battery, and AVRCP only in the other direction.

**What is missing today:**
- RFCOMM: HFP runs over RFCOMM, a serial multiplexer on L2CAP PSM `0x0003`. Haiku's stack never had it.
- SCO and eSCO audio: `h2generic` sets `BT_SCO_NOT_WORKING` and starts no isochronous transfers (a standing transfer on the MT7922 starved the events, see the note in `h2generic.cpp`). The microphone needs isochronous USB transfers started only while a voice link exists, an HCI SCO path, and a voice codec.

**Phases (each its own PR):**
- **7a. RFCOMM in user space**, in `bluetooth_server` (or a small R5 library if a second program needs it), on an L2CAP socket on PSM 3: frames with FCS, the multiplexer control channel (DLC 0), PN, MSC, credit-based flow control, a server channel number in an SDP record. No kernel code. Testable in QEMU only against itself (a loopback test of the frame and FCS code, and a fuzzer target for the frame parser, 60 s).
  - **As built (16 Nov 2026; nothing on hardware yet, and no profile uses it until 7b):** in `bluetooth_server`, MIT, written from RFCOMM 1.2 and TS 07.10 (no third-party code read).
    - `RFCOMMMux.h`/`.cpp`: no I/O, no threads, no Haiku headers, so the test and the fuzzer build it unchanged. Frames (SABM, UA, DM, DISC, UIH; one or two length bytes; the credit byte; the FCS over address and control for UIH, and also over the length for the others). DLCI 0 control: PN, MSC, Test, FCon/FCoff, RPN (answered with 9600 8N1), RLS, NSC for unknown commands. `Mux` is one session with one data DLC. As initiator: SABM 0, PN (credit flow asked, N1 127, 7 credits), SABM on DLCI `channel × 2` (direction bit 0), MSC (signals `0x8d`). It answers the other side's MSC, PN, Test, FCon/FCoff, RPN, RLS and DISC, and sends DM for a DLC it does not have. Every wait ends after 20 s (`kTimeout`). Received data waits in a 2048-byte buffer; R5 only gives credits for the room it has (top-up at 3 or fewer), so data is never dropped. Without credit flow (an RFCOMM 1.0 device) the MSC FC bit and FCoff stop sending. The responder side exists for the loopback test.
    - `RFCOMMLink.h`/`.cpp`, the API for 7b: `RFCOMMLink::Connect(address, channel, timeout, &link)` opens L2CAP PSM 3 and the DLC; `Send(data, length, timeout)` waits for credit; `ReadLine(buffer, size, timeout)` gives the next line up to a CR or LF; `Close()` (and the destructor) sends DISC on the DLC and on DLCI 0. A reader thread per link runs the socket (receive timeout 250 ms) and the timeouts. One thread uses a link at a time. One link per device: a second session to the same headset is not supported (RFCOMM allows only one).
    - The channel: `BluetoothServer::R5RFCOMMChannel()` reads ServiceClassIDList (0x0001) and ProtocolDescriptorList (0x0004) of the records SDP already reads, `R5FindRFCOMMChannel(address, 0x111E, &channel)` looks a paired device up. When SDP finds a Hands-Free record, the syslog says `hands-free service on RFCOMM channel <n>` (no address).
    - After stick 51 (17 Nov 2026; the WH-1000XM3 paired, SDP ran, no channel was found): the SDP answer is read by R5's own data element parser (`SDPParse.h`, MIT, from Core 5.4 Vol 3 Part B). Haiku's `SDPDataIO` read the whole answer in one pass and lost its step on a Nil, a URL or a 128-bit integer, which dropped that record and every record after it. Now each element is stepped over by its own length; attributes are stored as before (numbers, `sdp_uuid`, strings, sequences as their contents; an alternative as its first sequence). When an audio device's (or an unknown device's) browse gives no Hands-Free channel, a Service Search Attribute Request for `0x111E` with `0x0001`, `0x0004`, `0x0009` and `0x0311` follows, with its continuation states. Each answer logs one line without addresses, e.g. `sdp: 6 records: 0x1000 0x110b 0x110e 0x111e ...`, and an audio device without a Hands-Free record logs `hfp: no hands-free record`. Host test: `scripts/fuzz-bt.sh sdp` (a made-up five-record answer in pieces of any size, then damaged copies).
    - Tests: `bt_rfcomm_test` (regular image, `run-qemu-smoke.sh`): frames against bytes from TS 07.10 (SABM 0 `03 3F 01 1C`, UA 0 `03 73 01 D7`), malformed frames, PN and MSC bytes, the SDP channel of a Hands-Free record (16- and 128-bit UUIDs, broken lengths), two muxes back to back (open, data both ways, 20 frames through 7-credit windows, close, a refused DLC, a timeout), two `RFCOMMLink` objects over ports with their reader threads (lines, 4000 bytes, close), and `Connect()` without a radio. `scripts/fuzz-bt.sh rfcomm`: parsers, build-and-parse round trips, and a mux in both roles fed random frames with a right FCS.
    - Limits: not tried against a real headset (QEMU has no radio). The L2CAP connect waits as long as the kernel's own timeout, not the caller's. No RFCOMM server for other devices to connect to (R5 only connects out), and no SDP record of R5's own for it.
- **7b. HFP service level connection, without audio.** R5 is the Audio Gateway (the side a phone takes); the headset is the Hands-Free unit. The AT exchange of HFP 1.8: `BRSF`, `CIND`, `CMER`, `CHLD`, `BIND`/`BIEV` (HF indicators, indicator 2 is the battery), plus the Apple extension `AT+XAPL`/`AT+IPHONEACCEV` that many headsets use for the battery. Volume (`VGS`, `VGM`). The battery goes to `BT_MSG_R5_GET_PAIRED` ("battery") and so to My devices; the Deskbar item shows it with `R5_LEVEL_BATTERY`. Connected after A2DP, so it never delays music.
  - **As built (16 Nov 2026; nothing on hardware yet):** in `bluetooth_server`, MIT, from HFP 1.8 and Apple's accessory design guidelines (for `AT+XAPL` and `AT+IPHONEACCEV`).
    - `HFPAgent.h`/`.cpp` (no I/O, like `RFCOMMMux`): one AT line in, the AG's answer out (each line in CR LF). AG features `0x0400` in `+BRSF` (HF indicators only; no calls, voice recognition or codec negotiation before 7c, and no extended error codes, so failures stay a plain `ERROR`). `+CIND` lists service, call, callsetup, callheld, signal, roam and battchg, with the values `0,0,0,0,5,0,5`. The SLC is up at `AT+CMER`. `+CHLD: (0)`. HF indicators: only indicator 2 (battery), `+BIND: (2)` and `+BIND: 2,1`; `AT+BIEV=2,<0-100>` sets the battery. Apple: `+XAPL=iPhone,2` (the fixed token of that protocol; only battery reporting), `AT+IPHONEACCEV` key 1 (0–9 is 10–100 %). `VGS`/`VGM` 0–15 are kept and logged. `ATA`, `AT+CHUP`, `AT+BLDN`, `AT+BVRA`, `ATD` are buttons: logged, answered `ERROR` (there is no call). `AT+CKPD` (headset profile) is logged and answered `OK`. `NREC`, `CMEE`, `CLIP`, `CCWA`, `COPS`, `BIA`, `BCS`, `CLCC`, `CNUM`, `BTRH?` get `OK`, `COPS?` gets `+COPS: 0`, a bare `AT` gets `OK`, anything else `ERROR`. The SLC counts as up at `AT+CMER` even when BIND follows, so a headset that skips BIND still gets its session.
    - `HFPGateway.h`/`.cpp`: `NotifyServices()` (the link is encrypted and SDP is read) starts a session for a device with a Hands-Free record, one per device. The thread waits 0.5 s (5 s until 17 Nov 2026: the WH-1000XM3 on stick 54 ended the link 2 s after SDP, and nothing else opens a profile right after pairing), then `RFCOMMLink::Connect()` (30 s) and the AT loop. Without an SLC in 30 s the session ends. A session that never reached the SLC (a refused channel, a headset still busy with A2DP) tries again twice, 10 s apart, but only while the device still has its link (`_R5DeviceConnected()`), so R5 never pages a headset that left. A `DeviceReady()` while an attempt runs asks for one more after it (the device dropped and came back); one for the same link is dropped once the SLC is up. When the server quits, HFP stops first: `RFCOMMLink` takes a cancel flag, so the DLC wait ends within 250 ms and `Close()` does not wait for answers; only an L2CAP connect in progress keeps the kernel's timeout. Syslog, without addresses: `hfp: service level connection up, headset features <hex>`, `hfp: battery <n> %` (when it changes), `hfp: button <word>`, `hfp: volume speaker <n> microphone <n>`, `hfp: session ended`.
    - The battery: `BT_MSG_R5_GET_PAIRED` "battery" for a connected Classic device is the HFP value (-1 without a session or a report), so My devices shows it. The Deskbar item asks for the paired devices with each poll (5 s) and shows each connected device with a battery as a menu line: the `R5_LEVEL_BATTERY` glyph, then "<name>: battery <n>%". LE devices with the Battery Service show there too. While the server cannot be reached the list is empty, and an error answer replaces no list.
    - Tests: `bt_rfcomm_test` has the AT commands alone (SLC, BIND/BIEV, Apple battery, volume, buttons, refusals) and, on Haiku, `HFPGateway` itself with a scripted headset over ports: SLC and battery 80, one session per device, a retry after a failed connect, no connect without a link, giving up after the retries, and `Stop()` during the 30 s open wait (must take under 2 s). `scripts/fuzz-bt.sh hfp`: random lines and known commands with random arguments; every answer ends in OK or ERROR and fits.
    - Limits: not tried with a headset. R5 has no Audio Gateway SDP record and no RFCOMM server, so a headset cannot start HFP itself; R5 always connects. If a headset wants the AG record first, it may refuse; the 5625U boot shows that. Volume is logged, not yet tied to the Media volume. No `+CIEV` is sent (no calls). The Settings page and the Deskbar refresh every few seconds, so a new battery value can take that long to show.
- **7c. Voice: eSCO with mSBC (wideband) and CVSD (narrowband).** `h2generic`: isochronous transfers on the alternate setting the voice link needs, started at Synchronous Connection Complete and stopped at its disconnection. HCI SCO packets up and down. An own MIT SBC decoder for mSBC (the encoder exists), CVSD through the controller's air coding where it offers it. A Media Kit input node "Bluetooth headset microphone". Only on the 5625U: QEMU has no radio.
  - **As built (17 Nov 2026; nothing on hardware, and built from `main` without 7b, so no voice link is opened yet):** MIT, written from Core 5.4 (Vol 4, Part B, 2.1; Part E, 5.4.3, 7.1.26, 7.1.27, 7.7.5, 7.7.35), HFP 1.8 (4.11.3, 5.7, appendix A) and A2DP appendix B. No third-party code read.
    - **Off by default (owner, 16 Nov 2026).** The voice path runs only when `/boot/home/config/settings/kernel/drivers/h2generic` (the driver settings file under `settings/kernel/drivers`, as for `radeon_hd`) has the line `bt_voice true`; the image ships no such file. It is read once, when the driver loads, so a change needs a restart. With the setting off, `h2_voice_enabled()` is false: no voice node is published, no extra thread runs, the event path only tests that flag, and the attach still selects interface 1, alternate setting 5 as before, with no isochronous transfer queued. With it on, the syslog says `h2generic: voice enabled (bt_voice)`.
    - **Kernel** (`h2generic/h2voice.cpp`, `h2voice.h`, `h2sco.h`): with `bt_voice`, interface 1 starts at alternate setting 0 (no bandwidth). `event_complete()` hands the events that go up to a watcher (`h2sco.h`) that follows event boundaries across transfers and keeps only Synchronous Connection Complete (status 0, SCO or eSCO) and Disconnection Complete. One voice link per radio. A kernel thread ("h2generic voice") then picks the alternate setting with the smallest isochronous packets that hold 9 bytes per frame (transparent air mode, mSBC) or 17 (16-bit PCM, CVSD), never above 64 bytes, switches to it and keeps two transfers of 8 isochronous packets queued; at the disconnection (or when the radio closes) it cancels them and returns to setting 0. Log lines: `h2generic: voice on (<radio>, transparent|CVSD), alternate setting <n>, <size>-byte packets`, `h2generic: voice off (<radio>)`. No address is logged.
    - **SCO packets:** the isochronous packets are put together into whole HCI SCO packets (a packet starts at an isochronous packet; a bus error or a header with another handle drops what was collected, `h2sco.h`) and kept in a ring of 32 packets that drops the oldest when full. Every length from the radio is checked against the endpoint size and the SCO length byte. The old Haiku `sco_rx_complete()`/`submit_rx_sco()` stay unused: their buffer pool hands the same buffer to every transfer.
    - **The voice node** `/dev/bluetooth/voice/<n>` (`<R5BluetoothVoice.h>`), published with each radio only while `bt_voice` is on, outside `bluetooth/h2` so `bluetooth_server` does not take it for a radio: uid 0 only, one opener. `read()` gives one whole SCO packet or 0 bytes after 100 ms; `write()` takes one whole packet on the link's handle with Packet_Status 0 and sends it in isochronous packets of the endpoint size, at most 8 on their way (`B_WOULD_BLOCK` after that); ioctl `R5_BTVOICE_GET_LINK` gives handle, air mode, alternate setting, packet counts. User memory only through `user_memcpy()` after `IS_USER_ADDRESS()`.
    - **Decoder** (`bluetooth_audio/sbc_decoder.cpp`): SBC (all A2DP modes) and mSBC (sync `0xad`, 16 kHz mono, 15 blocks, 8 subbands, bitpool 26), with the encoder's bit allocation, every header field and the CRC checked. The encoder got `InitMSBC()` (the A2DP path is unchanged). The CRC of mSBC covers the two reserved header bytes as they are sent; that reading of HFP 1.8, A.1, is to be confirmed with a headset. `msbc.h` finds the 60-byte H2 packets (`0x01`, `0x08`/`0x38`/`0xc8`/`0xf8`, frame, pad) in the SCO payloads and counts frames the sequence numbers say are missing.
    - **CVSD** goes through the radio's air coding: R5 asks for Voice_Setting `0x0060` (16-bit linear PCM, 8 kHz), and the node doubles the rate by interpolation.
    - **Media node "Bluetooth headset microphone"** (`BluetoothMicNode.cpp`, `VoiceSource.cpp`): a physical audio input, 16 kHz mono float in 15 ms buffers, silence while there is no voice link (also while `bt_voice` is off). For every SCO packet that comes in one goes back with encoded mSBC silence (or zero PCM), so the headset's side of the link is not starved. 40 ms are buffered before samples go out; more than 200 ms are cut back to 60 ms. `DefaultManager` never makes it the default input by itself, as for the "Bluetooth audio" output. Log lines: `bluetooth_audio: headset microphone on (mSBC 16000Hz|CVSD 8000Hz)`, `... off (<n> packets lost)`.
    - **For the HFP side** (`bluetooth_server/VoiceLink.h`, header only, not yet called): the codec choice after AT+BAC (mSBC when both sides have it, CVSD otherwise), the settings T2, T1, S4, S3, S1 and D1 of HFP 1.8 table 5.8 in the order to try, and the bytes of Setup Synchronous Connection and Accept Synchronous Connection Request.
    - **What joins with #4333 (7b) after it is merged:** in `HFPGateway.cpp`, set the codec negotiation bit (9) in the AG's `+BRSF` when `bt_voice` is on; answer AT+BAC by storing the list; when audio is wanted, send `+BCS:<voice::ChooseCodec()>`, wait for AT+BCS, then send `voice::BuildSetup()` on the headset's ACL handle with the first setting of `voice::Fallbacks()` and the next one after a failed Synchronous Connection Complete; without codec negotiation, CVSD. In `LocalDeviceImpl.cpp`, a Connection Request with link type SCO or eSCO from a paired headset that has an HFP link is answered with `voice::BuildAccept()` (S4 or D1), not with the ACL Accept Connection Request. Nothing in the kernel or the media node changes for that.
    - **Joined with 7b (17 Nov 2026, after #4333; nothing on a radio yet):** with `bt_voice`, bluetooth_server reads the same driver settings line once at start (`load_driver_settings("h2generic")`). The HFP agent then sets codec negotiation (bit 9) in `+BRSF`, keeps the `AT+BAC` list, takes `AT+BCS` and `AT+BCC`; without `bt_voice` none of this changes. When a program connects to "Bluetooth headset microphone", the node sends `BT_MSG_R5_AUDIO_VOICE` (bool "on", admin port, uid 0 only) and `false` when it disconnects. The first HFP session with an SLC then sends `+BCS:<mSBC or CVSD>` when both sides negotiate codecs, waits up to 3 s for `AT+BCS`, and asks the radio (`LocalDeviceVoice.cpp`) for Setup Synchronous Connection on the headset's ACL link with T2, T1 (mSBC) or S4, S3, S1, D1 (CVSD) in turn; without codec negotiation it is CVSD at once. A refused or failed setup tries the next setting. A voice Connection Request from the headset is accepted (Accept Synchronous Connection Request, the codec's first eSCO setting, or D1 for SCO) only while the microphone is wanted for that headset, and turned down with Reject Synchronous Connection Request otherwise; before, it went into the ACL path and marked the device as connecting. The link ends with Disconnect (0x13) when the microphone is let go or the HFP session ends. Log lines without addresses: `hfp: microphone wanted|no longer wanted`, `voice: setting up <codec> (<setting>)`, `voice: link up (eSCO|SCO, <codec>, air mode <n>)`, `voice: setup failed (<status>)`, `voice: link down (<reason>)`, `voice: a voice link request was turned down`. Tests: the agent's codec commands on the host and in `bt_rfcomm_test`; `HFPGateway` over ports with a headset that sends `AT+BAC=1,2` and answers `+BCS: 2`, which opens an mSBC link and closes it when the microphone is let go; `fuzz-bt.sh hfp` with and without codec negotiation. Not tested: the HCI commands against a radio, and whether the Sony XM4 takes mSBC over this setup.
    - **Tests without a radio:** `bt_voice_test` (regular image, `run-qemu-smoke.sh`) and `scripts/test-voice.sh` (host, ASan and UBSan) run the same checks (`voice_checks.h`): mSBC through encoder, H2 packets, 24-byte SCO payloads, deframer and decoder (about 44 dB on a tone), SBC at 16, 44.1 and 48 kHz through the decoder, a damaged and a short frame refused, a lost packet counted, random frames; the event watcher however the events are cut, the alternate setting choice, SCO reassembly with a lost piece and a wrong handle, the ring, the transmit check; the HCI command bytes. In QEMU also: the add-on lists the microphone as an input, the node runs with one 16 kHz mono float output and is not the default input, and there is no voice node without `bt_voice`. `scripts/fuzz-bt.sh sco` fuzzes `h2sco.h`, the deframer and the decoder.
    - **Limits:** nothing tried on a radio: not on the 5625U, not with the Sony XM3 or XM4, and the isochronous path (alternate settings, `queue_isochronous`) never ran; whether the MT7922 keeps its events with a voice link up is the open question that kept this off. Only one voice link per radio. No packet loss concealment (a lost frame is silence). The headset hears silence: there is no speaker path. A radio that puts a SCO header in the middle of an isochronous packet would lose packets. ARM64 and RISC-V 64 were not built or tested.

## 4. The owner's choices

1. **Turning the radio on and off.** Scanning, pairing, connecting and choosing the audio output need no lock. Turning the radio on or off is behind the public `libr5ui.so` administrator lock (`distro/ui/AdminLock.h`).
2. **Paths on disk.** Pairing keys in `/boot/system/settings/bluetooth/` (uid 0, mode 0700). The audio choice per person in `~/config/settings/Media/bluetooth_audio`, found with `find_directory(B_USER_SETTINGS_DIRECTORY)`. There is no `settings/R5/` directory anywhere in R5, and `bluetooth_audio` is a Media add-on, so it sits next to the other Media settings.
3. **Crypto library for ECDH P-256.** `openssl3` (`libcrypto`, Apache-2.0), already in `distro/UserBuildConfig` (line 25).
4. **Test hardware for VirtualBox.** The MT7922 (`0x13d3:0x3567`) of the 5625U is passed to the `R5OS` VM with a USB filter. What that means:
   - While the VM runs, Windows has no Bluetooth; a headset or mouse through Windows does not work then. After the VM stops, Windows gets it back. If not, turn the adapter off and on once in Device Manager.
   - In the VM, R5 uses the same `h2mediatek` firmware path as on the stick, so the VM tests the real path.
   - `scripts/run-vbox-r5.ps1` gets an option that sets the USB filter for `0x13d3:0x3567`, off by default, so it does not happen by accident. First check the real vendor and product ID with `VBoxManage list usbhost`.
   - No separate dongle is needed. If passthrough fails (Windows does not let go of the device), a CSR dongle from a known brand is the fallback.
