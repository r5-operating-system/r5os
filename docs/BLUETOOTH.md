# Bluetooth on R5

This is the plan for Bluetooth on R5 Operating System: what is already in the tree, where each part goes, and the steps that get there. Each step is its own small pull request with a pass rule. The owner approved this plan; the choices in section 4 are the owner's.

Nothing in this document is built yet unless it says so.

## 0. Before step 0: VirtualBox USB passthrough and test hardware

QEMU has no Bluetooth hardware. Before step 0 we check USB passthrough in VirtualBox.

- The Windows host has the Oracle VirtualBox Extension Pack 7.2.22 (`Usable: true` in `VBoxManage list extpacks`). The `R5OS` VM already has `xHCI USB: enabled`, with no USB filter yet.
- Chosen: pass the built-in MT7922 of the 5625U to the VM (section 4, choice 4). The other options, for reference:
  - **CSR** (for example CSR8510 A10, `0x0a12:0x0001`, generic USB class `0xE0/0x01/0x01`): works in `h2generic` without extra firmware. Cheap CSR8510 clones often do not work, also not on Linux; buy one from a known brand.
  - **Realtek** (`0x0bda`) and **Qualcomm** (`0x0cf3`): no firmware loader before step 7, so they do not work as a dongle.
  - **Intel** (`0x8087`): needs `bt_firmware` (see `h2generic.cpp`).
  - **MediaTek MT7922** (`0x13d3:0x3567` in the 5625U): `h2mediatek.cpp` is already in `distro/`. It is the built-in radio of the 5625U, which we also test bare metal from the USB stick. Passing it to VirtualBox takes Bluetooth away from Windows while the VM runs.
- **5625U bare metal (MT7922):** USB sticks are costly, so hardware tests on the 5625U are bundled into one stick per few steps. The owner writes the stick with `scripts/write-stick.py`, after VirtualBox works first.

## 3. Steps

Each step is its own small pull request. It is built for AMD64 with `scripts/build-locked.sh` (apply and jam under one build lock, `/home/nickr/r5os/.r5-build.lock`; never `apply-overlay.sh` and `jam-r5-raw.sh` one after the other), and kept building for ARM64 and RISC-V (not tested). QEMU runs only on an own copy of `r5-os.image`, never through `scripts/run-qemu-r5.sh`, which stops every QEMU.

**How the fuzzers run (steps 1a, 1b, 1c).** Like `scripts/fuzz-midi2.sh`, the Bluetooth fuzzers run in WSL on the host (`g++ -std=c++17 -fsanitize=address,undefined -fno-omit-frame-pointer -g -O1`). The kernel parsers (the `hci` event and packet parser, and the `l2cap` packet and signalling parser) are compiled on their own with small host stub headers (`-I scripts/bt-host`, like `scripts/midi2-host`), without the whole Haiku kernel. `scripts/fuzz-bt.sh` and `scripts/bt-host` are new in step 1a. Each target runs 60 seconds.

### Step 1a (PR 2): `h2generic` HCI timeouts, safe reassembly, HCI fuzzer

- **What:** in `distro/kernel/src/add-ons/kernel/drivers/bluetooth/h2/h2generic/`: a hard HCI command timeout. A command without a Command Complete or Command Status within 2 s (Linux `HCI_CMD_TIMEOUT`) gets a Command Status with error `0x1F` (Unspecified Error) for that opcode, the timeout is logged with the opcode, and a real answer that still comes later is dropped (`h2command.h`). In `distro/kernel/src/add-ons/kernel/bluetooth/hci/`: the packet reassembly moves to `hci_assemble.h`, without the `panic()` on a split event and without the endless loop on SCO.
- **Not in this step (owner, 15 Nov 2026):** the Event Mask and the LE Event Mask. An HCI Reset from the kit (`LocalDevice::Reset()`) clears what a driver sets, so `bluetooth_server` sets them after every reset: the Event Mask in step 4, the LE Meta event and the LE Event Mask in step 6.
- **Checked (16 Nov 2026), which events each step needs:** after a reset the Event Mask is `0x00001FFFFFFFFFFF`, bits 0 to 44 (Core 6.0, Vol 4, Part E, 7.3.1); bit *n* is event code *n* + 1. Steps 1a to 3b use only events in that default (command answers, inquiry results, connections). Steps 1b and 1c add LE fixed channels and CoC to `l2cap`, but no LE link exists before step 6 asks for LE events, so they are tested with the fuzzer and the ABI test only. Step 4 needs Secure Simple Pairing events that are not in the default: IO Capability Request and Response, User Confirmation Request, User Passkey Request, Remote OOB Data Request and Simple Pairing Complete (codes `0x31` to `0x36`, bits 48 to 53), User Passkey Notification and Keypress Notification (`0x3B`, `0x3C`, bits 58 and 59). `LocalDeviceImpl.cpp` already waits for some of them, so on a controller that keeps the default they never arrive. Step 5 needs nothing new. Step 6 needs LE Meta (`0x3E`, bit 61).
- **Required checks:** manual SMAP review, a QEMU boot with SMAP, and `scripts/fuzz-bt.sh hci 60` in WSL (60 seconds of ASan and UBSan on the separately compiled HCI event and packet parser).
- **Pass:** QEMU SMAP boot without kernel panic, log line `hci_fuzz: 60s 0 crashes`, and in VirtualBox with the passed-through radio: `h2generic: controller ready`.

### Step 1c (PR 4): `l2cap` CoC and EATT, ISO endpoints prepared

- **What:** LE credit-based flow control (CoC) in `distro/kernel/.../l2cap/`, and recognition of the ISO USB endpoints in `h2generic`.
- **Pass:** QEMU SMAP boot, `l2cap_fuzz: 60s 0 crashes`, and `l2cap_coc_test: ok`.
- **Moved (16 Nov 2026, while the owner slept; open to change):** this step runs just before step 6, not after 1b. CoC and EATT run over the LE signalling channel of an LE link, and the ISO endpoints carry LE Audio (step 7); no LE link exists before step 6 asks for LE events, so nothing could use or test them earlier than the fuzzer. Built next to step 6, CoC shares the fixed-channel socket interface and gets a real LE link to test against.
- **As built (16 Nov 2026, one branch with step 6; nothing on hardware yet):**
  - **LE links in the kernel.** `btCoreData` (now in `distro/`) registers an LE link from LE Connection Complete and both Enhanced Connection Complete events, as an `HciConnection` of type `R5_HCI_LINK_LE` whose address is a `sockaddr_l2cap_le` (with the address type). It keeps the LE buffer length from the answer to LE Read Buffer Size, and `PostACL()` splits LE packets by it. Found while building: `AddConnection()` added a connection that already existed (data before the Connection Complete event) to the list a second time, which breaks the list; fixed.
  - **The socket interface** is `<R5BluetoothLE.h>` (private header, MIT): `sockaddr_l2cap_le` with channel, address type and mode. A fixed-channel socket (ATT `0x0004`, SMP `0x0006`, uid 0 only, one each) gets every PDU of that channel from every LE link with `recvfrom()` and sends with `sendto()`; bluetooth_server holds both. The LE signalling channel `0x0005` is served in the kernel: Connection Parameter Update (accepted within the limits of Vol 6, Part B, 4.5, then LE Connection Update), LE credit-based (`0x14`, `0x15`) and enhanced credit-based connections (`0x17`, `0x18`, up to five channels, the mode EATT uses on PSM `0x27`), Flow Control Credit and Reconfigure. Credit-based channels split an SDU into K-frames by the remote's MPS and credits and put received frames back together (`l2cap_coc_rx_frame()` in `l2cap_parse.h`, also in the fuzzer); a frame without a credit, too long, or past its SDU closes the channel. Our side: MTU 1024, MPS 247, 10 credits, given back while the receive queue has room.
  - **Fixed on the way** (Haiku code): closing a socket that was bound but never listened asked a command identifier of a NULL connection; a full receive queue leaked the buffer; `_SendQueued()` wrote the L2CAP header into a buffer `PostACL()` already owned; `htole32` was the 16-bit swap. From the independent review: the HCI receive thread holds the device list lock while it delivers a packet up, and every L2CAP sender held its endpoint lock while `PostACL()` took that list lock, a deadlock (also for Classic); L2CAP now sends through one send thread, `l2cap_tx.cpp`, without its locks. A packet is matched to the link it came on (no longer the first link of its address), and a channel only takes data, a disconnection or a configuration from its own link.
  - **Not in this step:** the ISO USB endpoints of `h2generic` (LE Audio, step 7). bluetooth_server uses the fixed ATT channel for GATT; EATT channels can be opened through the socket, but bluetooth_server does not open them yet.
  - **Checks:** `scripts/fuzz-bt.sh l2cap 60` (now with the LE codes and the frame reassembly), `bt_l2cap_coc_test` in QEMU with SMAP, manual SMAP review (no new user pointer in the kernel: addresses come through the socket layer, which copies them).

### Step 4 (PR 8): Classic HID (BR/EDR mouse and keyboard on PSM `0x11` and `0x13`) and SSP passkey

- **What:**

Checked: the `case` lines for IO capability, user confirmation (Numeric Comparison) and simple pairing complete are at lines 369–384. `HCI_EVENT_USER_PASSKEY_REQUEST` is expected at line 1795 but handled nowhere. This step adds `HCI_EVENT_USER_PASSKEY_REQUEST` and `HCI_EVENT_USER_PASSKEY_NOTIFICATION` (Passkey Entry, for keyboards).

### Step 5 (PR 9): Classic A2DP (R5's own MIT SBC) and AVRCP in `bluetooth_audio`

- **What:** a royalty-free SBC encoder (R5's own MIT code), AVDTP 1.3, and AVRCP (play, pause, volume) in `distro/media/bluetooth_audio/`, with an audio output choice per user. A real-time audio thread, and background scans paused while streaming.
- **Test path:** first VirtualBox USB passthrough, then a bundled 5625U bare-metal stick (written by the owner with `write-stick.py`) with the Sony WH-1000XM3 or XM4.
- **Pass:** log line `bluetooth_audio: streaming sbc 44100Hz`, steady audio without stutter on the Sony XM3 or XM4, and `bluetooth_audio: stream closed cleanly` on disconnect.
- **As built (16 Nov 2026; nothing on hardware yet, because Classic pairing on the MT7922 (reworked in #4314) is not yet confirmed with a headset):**
  - **SBC** (`sbc_encoder.cpp`, MIT): written from the A2DP 1.3.2 appendix B only. The analysis runs in floating point on the mixer's float samples, so nothing is rounded to 16 bits before SBC quantizes. All modes, 4 to 16 blocks, 4 and 8 subbands, Loudness and SNR, bitpool 2 to 250. The prototype filter is kept as the filter itself; the folding sign of the printed window is applied in code, with the reason in a comment.
  - **Quality choice** (`a2dp_proto.h`, `ChooseConfiguration()`): the mixer's rate (44.1 kHz; every sink must have 44.1 and 48 kHz), then joint stereo, 16 blocks, 8 subbands, Loudness, and the highest bitpool the headset allows within A2DP 4.3.2's 512 kb/s and one 672-byte media packet. That is bitpool 86 (509 kb/s) when the headset allows it, and the headset's maximum otherwise (53, 328 kb/s, on most). If the headset refuses its own maximum, R5 tries again once with 53, the A2DP high quality setting.
  - **AVDTP 1.3** (`A2DPSource.cpp`): one SBC source endpoint, as initiator (Discover, Get All Capabilities with a fallback to Get Capabilities, Set Configuration, Open, the media channel, Start) and as acceptor for every command a sink sends (including Delay Report, Abort and a General Reject for unknown ones). Only single-packet signalling. **Correction to the brief:** `bluetooth_server` did not listen on PSM `0x19`; the add-on listens on `0x19` and `0x17` itself while its node exists. `bt_l2cap_abi_test` now accepts `0x19` as held by bluetooth_audio.
  - **Who may connect:** the headset chosen by the person who signed in, or, with no choice, a device that bluetooth_server says is paired (new `BT_MSG_R5_AUDIO_PAIRED`, uid 0 only). Anything else is refused and logged without the address.
  - **Real-time thread** (`B_REAL_TIME_PRIORITY`): encodes and sends at the audio clock, 20 ms ahead, from a 40 ms ring; an empty ring is sent as silence so the headset never starves, and a ring that grows from clock drift is trimmed. The node reports that latency plus the headset's reported delay (capped at 0.5 s), so video stays in sync. After 5 s of silence the stream is suspended so the headset can sleep; the next sound starts it again, keeping the last 150 ms.
  - **Scans paused:** while the stream runs, `bluetooth_server` refuses Inquiry and Periodic Inquiry (`BT_MSG_R5_AUDIO_STREAMING`, uid 0 only, ends by itself when media_addon_server's team is gone). A scan that already runs is not stopped.
  - **AVRCP** (PSM `0x17`): R5 asks for the headset's events and registers for volume changes; with absolute volume the node's Volume parameter is the headset's volume (R5 takes the headset's level first, never jumps to its own), without it the gain is applied to the samples. Play, pause and stop from the headset are accepted and start or suspend the stream. UNIT INFO and SUBUNIT INFO are answered; other PASS THROUGH keys get NOT IMPLEMENTED.
  - **Output choice per person:** `~/config/settings/Media/bluetooth_audio` (flattened BMessage, `device`). media_addon_server runs as uid 0, so the add-on reads the file of the account Login named in `/boot/system/settings/r5-desktop-session` (as the registrar does) and never writes it. The person writes it with `bt_audio use <address>` or `bt_audio off` (`find_directory(B_USER_SETTINGS_DIRECTORY)`).
  - **Log lines:** `bluetooth_audio: streaming sbc 44100Hz`, then the mode, blocks, subbands, bitpool and rate; `bluetooth_audio: stream closed cleanly` after Close in either direction; `bluetooth_audio: stream ended: <reason>` otherwise. No addresses or keys.
  - **Open:** no SDP record for A2DP Source or AVRCP yet (`SDPServer` answers nothing), so a headset that checks R5's record before absolute volume may not offer it; play and pause do not reach the playing program; the headset choice is not on the Bluetooth page yet; the link is not checked for encryption before audio; the L2CAP socket does not report the headset's MTU, so packets stay within 672 bytes. ARM64 and RISC-V 64 were not built or tested.

### Step 6 (PR 10): BLE Secure Connections, extended advertising, BLE HID over GATT

- **What:** the socket interface for the LE fixed channels (ATT, SMP; dropped since step 1b); the LE Meta event (bit 61) added to the Event Mask of step 4, and the LE Event Mask, set by `bluetooth_server` after every HCI Reset, with only the bits the controller supports (safe for Bluetooth 5.x and 6.0); LE Secure Connections (ECDH P-256 through `openssl3` `libcrypto`), extended advertising, 2M PHY and subrating in `bluetooth_server`, and BLE HID over GATT (`bluetooth_le_hid` to `input_server` or `/dev/joystick/bluetooth/N`, 7.5 ms interval, cached report layout).
- **Test path:** VirtualBox USB passthrough and a second bundled 5625U stick.
- **Pass:** `bluetooth_server: smp sc pairing ok`, and a BLE mouse and keyboard move smoothly in `input_server`.
- **As built (16 Nov 2026, with step 1c; nothing on hardware yet):** `LEManager` in `bluetooth_server` (MIT; `LEManager.cpp`, `LEManagerSMP.cpp`, `LEManagerGATT.cpp`), one per radio.
  - **Setup after every reset:** on a controller with "LE Supported" (LMP bit 38) the Event Mask of step 4 gets LE Meta (bit 61); after it come Write LE Host Support, Read BD_ADDR, LE Read Local Supported Features, then the LE Event Mask with only the subevents the controller supports (Remote Connection Parameter Request, Data Length Change, Enhanced Connection Complete, PHY Update Complete, Extended Advertising Report each only with its feature), LE Read Buffer Size, the suggested data length 251 bytes (with Data Length Extension), 1M or 2M PHY (with 2M), the resolving list (with LL Privacy and a paired device's IRK) and the accept list. One LE command at a time. Log line: `bluetooth_server: hci<N> le event mask <mask> (extended|legacy scan)`.
  - **Scan:** while the Classic inquiry runs, an active LE scan (extended where the controller has it, legacy otherwise, never mixed). A connectable device with a name goes to the same scan list as a `BT_MSG_INQUIRY_DEVICE` answer, at most once a second; its class of device comes from the GAP appearance or the HID service (mouse, keyboard, gamepad), so the list shows what it is. No change in `libr5bt.so`.
  - **Pair:** the Pair button sends Create Connection as for Classic; for an address the LE scan found, bluetooth_server makes an LE link instead (LE Create Connection or Extended Create Connection, 7.5 to 15 ms interval, 5 s timeout) and pairs: Pairing Request with KeyboardDisplay, bonding and Secure Connections, no MITM asked by us. ## 4. The owner's choices

1. **Turning the radio on and off.** Scanning, pairing, connecting and choosing the audio output need no lock. Turning the radio on or off is behind the public `libr5ui.so` administrator lock (`distro/ui/AdminLock.h`).
2. **Paths on disk.** Pairing keys in `/boot/system/settings/bluetooth/` (uid 0, mode 0700). The audio choice per person in `~/config/settings/Media/bluetooth_audio`, found with `find_directory(B_USER_SETTINGS_DIRECTORY)`. There is no `settings/R5/` directory anywhere in R5, and `bluetooth_audio` is a Media add-on, so it sits next to the other Media settings.
3. **Crypto library for ECDH P-256.** `openssl3` (`libcrypto`, Apache-2.0), already in `distro/UserBuildConfig` (line 25).
4. **Test hardware for VirtualBox.** The MT7922 (`0x13d3:0x3567`) of the 5625U is passed to the `R5OS` VM with a USB filter. What that means:
   - While the VM runs, Windows has no Bluetooth; a headset or mouse through Windows does not work then. After the VM stops, Windows gets it back. If not, turn the adapter off and on once in Device Manager.
   - In the VM, R5 uses the same `h2mediatek` firmware path as on the stick, so the VM tests the real path.
   - `scripts/run-vbox-r5.ps1` gets an option that sets the USB filter for `0x13d3:0x3567`, off by default, so it does not happen by accident. First check the real vendor and product ID with `VBoxManage list usbhost`.
   - No separate dongle is needed. If passthrough fails (Windows does not let go of the device), a CSR dongle from a known brand is the fallback.
