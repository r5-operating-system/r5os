The Game Kit

R5's libr5game.so turns a game controller into named buttons and sticks: A, B, X and Y, the two sticks and the two triggers, in the order of SDL's standard gamepad, so a ported game finds them where it expects. It sits on top of Haiku's BJoystick, which stays as it is: a program that uses BJoystick keeps working and sees the controller's own button numbers. The code is R5's own and MIT.

How a controller gets its layout. The driver tells R5 the controller's USB vendor and product ID (a USB controller from its device descriptor, a Bluetooth one from its Device ID record). R5 looks that up in the community mapping database SDL_GameControllerDB, which ships unmodified with R5. A controller that is not in it still works: its raw buttons and axes are there, and the picture is built from what it reports.

As with BJoystick: open once, then call Update() every frame and read the values.

The standard layout. B_CONTROLLER_BUTTON_A is the lower face button, _B the right one, _X the left one and _Y the upper one, whatever is printed on them. Sticks run from -32768 to 32767 (left and up negative), triggers from 0 to 32767. Without a mapping these stay up and centered.

The product name, the IDs, USB or Bluetooth, the shape (PlayStation, Xbox, Nintendo, Sega Genesis, or unknown) and the battery in percent, or -1 when the controller does not say.

Which labels the person wants to see for this controller: Xbox letters or PlayStation symbols. A game uses LabelStyle() to show the right button in its prompts. The choice is made in Settings; only Settings calls the setters.

static status_t StartWatching(BMessenger target);
static status_t StopWatching(BMessenger target);

B_GAME_CONTROLLER_ADDED and B_GAME_CONTROLLER_REMOVED, with the string "device", when a controller is plugged in, paired, unplugged or turned off. No polling.

static game_controller_family LayoutFor(uint16 vendorID, uint16 productID);
static status_t SetLayout(uint16 vendorID, uint16 productID, game_controller_family layout);

The layout the person chose for a controller model in Settings: the shape, and a fixed mapping in the order that family's own controllers report their buttons. B_GAME_CONTROLLER_FAMILY_UNKNOWN means automatic: the mapping database. Only Settings calls the setter.

static status_t GetSavedMapping(uint16 vendorID, uint16 productID, char* mapping, size_t size);
static status_t SetSavedMapping(uint16 vendorID, uint16 productID, const char* mapping);
bool HasSavedMapping() const;

A setup the person made button by button with Set up buttons… in Settings, as text in SDL's mapping keys: "a:b0,b:b1,dpup:h0.1,leftx:a0,". Buttons and hats are numbered as the raw calls number them, axes in the order of RawAxisValue(); + and - take half an axis, ~ turns it round. NULL or an empty string removes it. Open() takes a saved setup first, then a chosen layout, then the database, so a change counts from the next Open(). Programs that use BJoystick still see the raw buttons.

Example

#include <GameController.h>

BGameController pad;
char name[B_OS_NAME_LENGTH];
if (pad.CountDevices() > 0 && pad.GetDeviceName(0, name) == B_OK
	&& pad.Open(name) == B_OK) {
	// every frame
	pad.Update();
	if (pad.IsButtonDown(B_CONTROLLER_BUTTON_A))
		Jump();
	float x = pad.AxisValue(B_CONTROLLER_AXIS_LEFT_X) / 32768.0f;
}

BGameControllerView

class
Declared in<GameControllerView.h>
Derived fromBView

A picture of the controller's own model, chosen by its vendor and product ID: the line drawings of the Gamepad Line Art Pack (CC0) for Xbox, PlayStation and Nintendo controllers, and R5's own drawing in the same style for the Sega Genesis family (the 8BitDo M30). Vector, scaled to the view, in the text color, so dark mode works; no logos. While a controller is open a pressed control fills with the accent color under the line, a pressed stick fills its cap, a moved stick shows a ring in the accent color off centre, and the analog triggers are two small caps over the shoulders that fill as far as they are pulled, with their value beside them ("L2 60%"). A controller without a mapping gets a picture built from what it reports.

status_t SetDevice(const char* deviceName);
BGameController* Controller();

Opens the controller and shows it live while the view is in a window; it reads the controller about 60 times a second and draws only when something changed. NULL closes it.

void SetTriggerMark(game_controller_trigger trigger, float position);

A tick across a trigger cap where a trigger effect starts, 0 to 1; below 0 removes it.

void SetFamily(game_controller_family family);
void SetLabels(game_controller_labels labels);

The still picture of a family, without a controller (PlayStation: the DualSense, Xbox: the Xbox Series controller, Nintendo: the Switch Pro Controller, Sega Genesis: the M30); and the labels on the face buttons of a picture built from what a controller reports (B_GAME_CONTROLLER_LABELS_AUTOMATIC: the controller's own choice). A model's picture shows what is printed on that model.

PictureBitmap()

BGameControllerView
static BBitmap* PictureBitmap(uint16 vendorID, uint16 productID, game_controller_family family, float width, float height, rgb_color lineColor);

Added at the end (17 Nov 2026). The still drawing of a model as a new bitmap, for a card or a list row: chosen as SetDevice() chooses it (the vendor and product ID, else the family's own picture), width by height pixels, transparent around the line, the line in lineColor, kept in shape and centred. Without a model and with B_GAME_CONTROLLER_FAMILY_UNKNOWN a plain outline. The caller owns the bitmap; NULL for an empty size. It needs a BApplication, because app_server draws it. Settings uses it for the cards of its BCardStrip and for the gray example when no controller is connected.

BBitmap* picture = BGameControllerView::PictureBitmap(pad.VendorID(), pad.ProductID(),
	pad.Family(), 56, 38, ui_color(B_DOCUMENT_TEXT_COLOR));
// draw it with B_OP_ALPHA, then
delete picture;

Rumble, triggers and motion

BGameController

Added at the end of BGameController (17 Nov 2026). For the DualSense, the DualSense Edge and the DualShock 4, over USB and Bluetooth, and rumble on any controller with HID force feedback (the USB HID PID page). Ask first with the Can and Has calls; a call the controller cannot do returns B_NOT_SUPPORTED.

bool CanRumble() const;
status_t SetRumble(float strong, float weak, bigtime_t duration);
status_t StopRumble();

strong is the heavy, slow motor, weak the light, fast one, each 0 to 1. It stops by itself after duration microseconds; 0 keeps it until the next call. Close() stops it.

bool HasTriggerEffects() const;
status_t SetTriggerEffect(game_controller_trigger trigger, game_controller_trigger_effect effect, float start, float strength);

DualSense only. B_CONTROLLER_TRIGGER_LEFT or _RIGHT; B_TRIGGER_EFFECT_OFF, _RESISTANCE (pushes back from the start position on), _CLICK (resists, then gives way) or _VIBRATION. start is where on the pull it begins, strength how hard, each 0 to 1. Close() sets both triggers free.

bool HasMotion() const;
status_t SetMotionEnabled(bool enabled);
bool IsMotionEnabled() const;
status_t GetMotion(game_controller_motion* motion) const;

Switch it on, call Update() every frame, then read the last sample: acceleration in g (x right, y up, z toward the player), rotation in degrees per second (pitch, yaw, roll) and the timestamp of the report. Not calibrated per controller.

pad.SetRumble(1.0f, 0.3f, 250000);       // a quarter of a second
if (pad.HasTriggerEffects())
	pad.SetTriggerEffect(B_CONTROLLER_TRIGGER_RIGHT, B_TRIGGER_EFFECT_CLICK, 0.4f, 0.8f);
if (pad.HasMotion())
	pad.SetMotionEnabled(true);
// every frame
pad.Update();
game_controller_motion motion;
if (pad.GetMotion(&motion) == B_OK)
	Steer(motion.rotation[1]);
Under the hood. The library builds each controller's own output report (with the CRC-32 Bluetooth needs) and sends it through a new joystick driver call; the report layouts were read from SDL's drivers (zlib), facts only. A DualSense or DualShock 4 over Bluetooth switches to its full reports after the first one; the driver keeps the buttons working for every BJoystick program. Not yet tested with a real controller.

BGameControllerMotionView

class
Declared in<GameControllerMotionView.h>
Derived fromBView

The motion of a controller: a BTiltLevel for the tilt and three BAxisBars for the turn, labelled Pitch, Roll and Yaw. The program reads the controller; the view only shows.

void SetMotion(const game_controller_motion& motion);
void Reset();
void SetTurnRange(float degreesPerSecond);

A sample: the level from the acceleration's x and z, the bars full at the turn range (360 degrees per second unless set). Reset() puts everything in the middle.

void SetEnabled(bool enabled);
bool IsEnabled() const;

False draws the level, the bars and their labels gray, as a disabled control: an example without a controller. True at first.

Where people see it

Settings, Devices, Game controllers: the controllers in a BCardStrip at the bottom, one card each with a small picture from PictureBitmap(); above it the live test of the chosen one with its layout, the button-label choice and Set up buttons… (a window that asks the person to press each control in turn), and Rumble, Motion and Trigger feedback beside the picture. Without a controller the page shows a gray example and a dashed card that opens the Bluetooth page. The Bluetooth page's Test buttons… opens it.

Not yet. Swapping buttons for old programs, lights and the touchpad; the Switch Pro and Xbox controllers over Bluetooth for rumble (phase 2). Rumble, Motion and Trigger feedback are shown for the controllers that have them. The battery shows only when the controller reports it in its input report (the HID Battery Strength usage). Tested in QEMU with virtual controllers fed to the Bluetooth HID driver; not yet with a real controller.
