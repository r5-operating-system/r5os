libr5admin.so

The Admin Kit

Some requests change the machine: an account, the clock, a driver, the Bluetooth switch. The service that carries them out runs as uid 0 and must know who asks. libr5admin.so gives it a sender that the kernel names, so no program can pretend to be another one.

Look here first. A new service that decides by its sender (an administrator, uid 0, a program with an unlock grant) uses this kit. Do not decide by BMessage::ReturnAddress() or IsSourceRemote().

Why not ReturnAddress()

A BMessage carries a reply messenger, and the sender chooses it: SendMessage(message, replyTo) puts any messenger there, also the one of Login or of another uid 0 program. Its team says nothing about who sent the message. Until November 2026 Login and bluetooth_server decided by that team, so any program could act as an administrator.

The kernel records the uid, group and team of the program that wrote each message on a port, and gives them to the port's reader (get_port_message_info_etc()). Nobody can change those. The Admin Kit reads requests from a port of their own, with those values.

Service side

functions
status_t r5_admin_port_start(const char* name, r5_admin_handler handler, void* cookie, port_id* port);

Creates the admin port and a thread that reads it. For every request it calls handler(request, sender, reply, cookie) on that thread, one at a time, and sends reply back. The handler locks what it touches, for most services be_app.

struct r5_admin_sender { uid_t uid; gid_t gid; team_id team; };

The sender as the kernel saw it. Check the uid for uid 0 or the group admin, and use the team for a grant.

bool r5_admin_port_reply(BMessage* message, port_id port);

In the service's MessageReceived(): answers R5_ADMIN_PORT_REQUEST with the port, so clients can find it. Returns false for any other message.

bool r5_admin_sender_allowed(const r5_admin_sender& sender);

True when the sender may change a machine-wide setting: uid 0, a member of the group admin, or a program the administrator lock was opened for (Login's grant). The same rule Login and the Bluetooth switch use. Added 22 Nov 2026 for the power service.

bool r5_admin_is_system_guest(uid_t uid);

True when uid is the guest account R5 made itself: login name guest, home /boot/home/users/guest, and the uid recorded in /boot/system/settings/r5-guest-uid (owned by uid 0, not writable by group or others). An older account that is only called "guest" is not the guest. Use it, never the name, before you hide something from the guest. Deskbar uses it for the guest menu. Added 24 Nov 2026.

void r5_admin_port_stop(port_id port);

Deletes the port and waits for its thread. Call it without holding the lock the handler takes.

static void
admin_request(BMessage* request, const r5_admin_sender& sender,
	BMessage* reply, void* cookie)
{
	MyServer* server = (MyServer*)cookie;
	if (!server->Lock())
		return;
	bool allowed = sender.uid == 0;
	reply->AddInt32("status", allowed ? server->Apply(request) : B_NOT_ALLOWED);
	server->Unlock();
}

r5_admin_port_start("my admin", admin_request, this, &fAdminPort);

Client side

function
status_t r5_admin_send(const BMessenger& service, BMessage* request, BMessage* reply, bigtime_t timeout = 5000000);

Asks the service for its admin port, checks that the port belongs to the service's team (a port with the same name made by another program gets nothing), sends the request and waits for the reply. Use it instead of BMessenger::SendMessage() for every request that changes something. A request may hold a password; the copy that was sent is cleared.

BMessage request(BT_MSG_R5_SET_RADIO);
request.AddBool("enabled", false);
BMessage reply;
status_t status = r5_admin_send(BMessenger(BLUETOOTH_SIGNATURE), &request, &reply);

Where it is used

Login carries out account changes, the unlock and its grant, the clock and time zone, and driver settings only on its admin port. Its normal messenger answers only the query (is this program unlocked?). The administrator lock in libr5ui.so and Users send through r5_admin_send(), so a grant belongs to the program that unlocked, for example Settings and every page in it.

bluetooth_server takes the Bluetooth switch and the requests of bluetooth_audio only on its admin port. The switch needs an administrator or a grant; the audio requests need uid 0.

The power service (power_daemon) writes the machine's power settings, the ones on the Power page, only after an admin request. Its handler checks the sender with r5_admin_sender_allowed() and writes the file itself; the page never writes it. Reading the settings and watching need no rights and go to its normal messenger. A program sends through BPowerRoster::SetSettings().

static void
admin_request(BMessage* request, const r5_admin_sender& sender,
	BMessage* reply, void* cookie)
{
	PowerManagementDaemon* self = (PowerManagementDaemon*)cookie;
	status_t status;
	if (request->what != kMsgPowerSetSettings)
		status = B_BAD_VALUE;
	else if (!r5_admin_sender_allowed(sender))
		status = B_PERMISSION_DENIED;
	else
		status = self->Policy().SetSettings(*request);
	reply->AddInt32("status", status);
}
